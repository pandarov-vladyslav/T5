## 1. Загальна інформація про модуль

Модуль реалізує базову авторизацію користувачів у навчальному Flask-застосунку з використанням SQLite.

Реалізовані можливості:
- реєстрація користувача з унікальним логіном;
- перевірка формату логіна та мінімальної довжини пароля;
- хешування пароля перед записом у базу даних;
- перевірка логіна та пароля під час входу;
- збереження `user_id` та `username` у Flask session;
- вихід із системи через очищення сесії.

Паролі зберігаються в полі `password_hash`, а не у відкритому вигляді. Для хешування та перевірки використано `generate_password_hash()` і `check_password_hash()` з `werkzeug.security`.

## 3. Аналіз сторонніх залежностей

У наданому `requirements.txt` вказано:

```text
Flask>=3.0,<4.0
pytest>=8.0,<9.0
```

У вихідному коді також безпосередньо імпортується `werkzeug.security`. Werkzeug встановлюється як залежність Flask, однак оскільки код проєкту напряму використовує його API, доцільно додати Werkzeug до `requirements.txt` як пряму залежність і зафіксувати перевірений діапазон версій.

| Компонент | Використання | Статус |
|---|---|---|
| Flask | Маршрути, Blueprint, HTTP-запити, сесії | Пряма залежність у `requirements.txt` |
| Werkzeug | Хешування та перевірка паролів | Використовується напряму в коді; зараз встановлюється транзитивно через Flask |
| pytest | Автоматизовані тести | Пряма залежність у `requirements.txt`, потрібна для розробки/тестування |
| SQLite (`sqlite3`) | Локальна база даних | Модуль стандартної бібліотеки Python, окремий пакет у `requirements.txt` не потрібен |
| `re`, `os` | Регулярні вирази та змінні середовища | Стандартна бібліотека Python |

Flask автоматично встановлює низку транзитивних залежностей, зокрема Werkzeug, Jinja, MarkupSafe, ItsDangerous, Click і Blinker. Точний набір і версії фактично встановлених пакетів у наданому архіві не зафіксовані: файл блокування залежностей (`requirements.lock`, `poetry.lock` тощо) відсутній. Тому повний перелік версій транзитивних компонентів потребує окремого формування після встановлення залежностей.

Офіційна документація Flask описує його залежності: https://flask.palletsprojects.com/en/stable/installation/

**Висновок щодо залежностей:** явних зайвих бібліотек у `requirements.txt` не виявлено. Водночас Werkzeug слід оголосити прямою залежністю, оскільки `auth.py` імпортує його безпосередньо. Для відтворюваного складання проєкту потрібно зафіксувати конкретні перевірені версії залежностей.

## 5. Результати Code Review

Під час перегляду вихідного коду встановлено таке.

### Позитивні моменти

1. Паролі не записуються до SQLite у відкритому вигляді: зберігається результат `generate_password_hash()`.
2. Для перевірки пароля використовується `check_password_hash()`.
3. SQL-запити виконуються з параметрами `?`, а не через конкатенацію введених користувачем рядків.
4. Логін перевіряється регулярним виразом; встановлено обмеження довжини логіна та пароля.
5. Перед створенням нової авторизованої сесії викликається `session.clear()`.
6. У конфігурації встановлені `SESSION_COOKIE_HTTPONLY=True` і `SESSION_COOKIE_SAMESITE="Lax"`.
7. Для тестів передбачена окрема тимчасова SQLite-база даних.

### Виявлені зауваження

1. **Werkzeug не оголошено прямою залежністю.** Він імпортується безпосередньо в `auth.py`, але відсутній у `requirements.txt`. Його слід додати явно.
2. **З'єднання SQLite може не закриватися вчасно.** Контекстний менеджер `sqlite3.Connection` керує транзакцією, але сам по собі не гарантує закриття з'єднання після виходу з `with`. Доцільно реалізувати явне закриття з'єднання, наприклад через власний контекстний менеджер або `contextlib.closing`.
3. **Обробка JSON має недолік.** `request.get_json(silent=True) or {}` не гарантує, що отримане значення є словником. Якщо клієнт надішле JSON-масив або рядок, наступний виклик `data.get(...)` може спричинити помилку сервера. Потрібно перевіряти тип JSON-об'єкта.
4. **CSRF-захист відсутній.** Для авторизації, що використовує cookie-based сесію, потрібно передбачити CSRF-захист для запитів, які змінюють стан, зокрема виходу із системи.
5. **Налаштування `SESSION_COOKIE_SECURE` ненадійно прив'язане до `FLASK_ENV`.** Прапорець стає `True`, лише якщо змінна `FLASK_ENV` дорівнює рядку `production`. Потрібно задавати це налаштування явною конфігурацією для production і перевірити його на цільовому середовищі.
6. **Потрібне обмеження частоти спроб входу.** У поточному коді немає захисту від автоматизованого підбору паролів.
7. **Немає обмеження розміру HTTP-запиту.** Доцільно встановити ліміт розміру запиту та обробляти некоректні або надмірні дані.
8. **Сесія Flask підписується, але не шифрується.** Підпис захищає цілісність cookie, але не приховує її вміст. Не слід зберігати в сесії секретні дані.
9. **Немає функцій відновлення пароля, підтвердження облікового запису та керування активними сесіями.** Це не обов'язково для навчального прикладу, але може бути необхідним для комерційного продукту залежно від його вимог.

## 6. Аналіз потенційних ризиків

| Ризик | Рівень для подальшого опрацювання | Пояснення |
|---|---|---|
| CSRF | Високий | Зміна стану через cookie-based сесію без CSRF-захисту може бути ініційована стороннім сайтом |
| Підбір паролів | Високий | Немає rate limiting або іншого обмеження спроб входу |
| Неналежне керування SQLite-з'єднаннями | Середній | З'єднання не закривається явно після операцій |
| Некоректний тип JSON | Середній | JSON, який не є об'єктом, може спричинити помилку сервера |
| Неправильне production-налаштування cookie | Високий | `Secure` може залишитися вимкненим, якщо `FLASK_ENV` не встановлено очікуваним чином |
| Відсутність фіксації версій | Середній | Оновлення залежностей може змінити поведінку або спричинити несумісність |
| Невизначена ліцензія власного коду | Середній | Немає `LICENSE` і підтвердженого рішення щодо умов розповсюдження |
| Недостатнє тестове покриття | Середній | Наявні тести охоплюють основні сценарії, але не всі помилкові типи JSON, CSRF, rate limiting і production-конфігурацію |

Рівні ризику є якісною оцінкою за результатами перегляду коду, а не результатом формального penetration test або кількісної оцінки загроз.

## 7. Рекомендації перед комерційним використанням

Перед використанням модуля в комерційному вебзастосунку рекомендується:

1. Додати Werkzeug до прямих залежностей і зафіксувати перевірені версії всіх пакетів, включно з транзитивними.
2. Виправити керування SQLite-з'єднаннями, забезпечивши гарантоване закриття.
3. Перевіряти, що JSON-запит містить саме об'єкт із потрібними полями; повертати контрольовану помилку замість 500.
4. Додати CSRF-захист для cookie-based сесій.
5. Явно встановлювати `SESSION_COOKIE_SECURE=True` у production, використовувати HTTPS та перевірити налаштування `HttpOnly` і `SameSite`.
6. Додати rate limiting, журналювання підозрілих спроб і механізм тимчасового обмеження входу.
7. Встановити обмеження розміру запиту та налаштувати безпечні HTTP-заголовки.
8. Додати тести на некоректні типи JSON, повторну реєстрацію, неправильні паролі, відсутній секретний ключ і production-конфігурацію.
9. Провести перевірку залежностей на відомі вразливості та сформувати SBOM (перелік компонентів програмного забезпечення).
10. Визначити ліцензію власного коду, додати файл `LICENSE` за обраною моделлю та включити необхідні повідомлення ліцензій сторонніх компонентів.
11. Провести незалежний security review і тестування в умовах, наближених до production.
